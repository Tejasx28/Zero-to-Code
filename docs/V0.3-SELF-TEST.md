# Test the full learning loop on yourself

Choose one language first. Keep the same browser and local address throughout the experiment. Avoid reading reference solutions, source answer keys, or maintainer checks before taking the learner tasks.

## Predict, play, and name the rule

1. Take the optional baseline honestly and record confidence. If skipped, leave the learning gain unmeasured.
2. In a briefing, predict before revealing. Use your own words, or choose “not sure yet.” A prediction is a thinking tool, not an automatically graded essay.
3. Enter the related simulation. Make a plan and test it. Inspect the state after each important move; use Step, Undo, or a slower replay when the change is unclear.
4. After a useful mistake, describe what the rule prevented and why. Ask for only the amount of hint you need.
5. At the game-to-code bridge, name the repeating rule, answer the related question, and arrange the algorithm steps. Explain what information the program must remember. Carry that explanation into the coding strategy notes.

## Write and investigate

6. Write the matching function yourself. Keep its contract, but choose your own valid approach. Close any example before reconstructing the code.
7. Predict one return value, then run the tests. Inspect a failing case’s input, expected result, and actual return before changing several lines at once.
8. In Python, replay the recorded trace and watch a variable change. Remember that line events show the state before the instruction runs. In Java, use the marked compiler line and test evidence; there is no Java variable replay yet.
9. Try an input of your own that could break the plan: an empty row, a duplicate, a boundary index, a missing target, or a negative value where the contract allows it. Custom experiments are ungraded.
10. Explain why the repaired program handles a new input. Passing output tests does not prove a particular algorithm or complexity.

## Transfer, then return later

11. Attempt a related problem. State what stayed the same and what changed: sorted versus unsorted input, remembering a maximum instead of a total, or removing only some stack items rather than reversing everything.
12. Take the independent task without outside help. It has no built-in hint or worked solution. Preserve both the first submission score and later revisions.
13. After three regular exercises pass, take the immediate concept snapshot without notes and export the diary.
14. Return after at least 48 hours, before reviewing, for the fresh memory check. Also rewrite one earlier function in a blank file as a manual coding-retention check.

## What should the website change?

| What happened | What to investigate |
| --- | --- |
| I won the game but cannot name its rule | The interaction-to-concept explanation |
| I know the rule but cannot arrange the steps | The concept-to-algorithm bridge |
| I can arrange steps but cannot write them | Language syntax and worked-example fading |
| I keep changing code without understanding failures | Test evidence, diagnostics, or trace guidance |
| I pass the familiar task but fail the related one | Whether the lesson taught a reusable idea |
| I succeed immediately but forget later | Retrieval practice and spacing |

Record the first point where outside help became necessary. Change one obstacle, then test with a fresh task or another beginner. Game progress, supported practice, unassisted coding, first-submission success, and delayed recall are separate observations.
