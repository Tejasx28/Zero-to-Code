# v0.4 direction — Make the code the interaction

## Product promise

DSA Quest starts with a beginner learning on themselves. The prototype succeeds when that learner can create a small general program, investigate its behavior, and reuse the idea without copying an example. Completion animations and game wins are supporting signals.

Keep the original discover-before-definition approach, but make discovery happen through code. Aim for roughly 75% writing, running, debugging and adapting code, with 25% short explanations and reflection. Validate that balance by observing a session.

## A smaller active path

The active React entry point is `ContractApp`. It presents three chapters:

1. Functions, inputs, and returned results.
2. Conditions, branches, loops, and accumulators.
3. Arrays, traversal, and changing sequences.

Five connected code games introduce the moves. Complete missing source in The First Contract; debug The Broken Gate; arrange executable lines in Relay Sequence; write a controller in Knightmare Navigation; implement traversal in The Memory Sweep. Python and Java run actual learner source. The route visual follows returned coordinates, rather than awarding a win for button steering.

Then use the Code studio starter, with fewer prompts. Seven regular tasks provide practice and related variations. Count-above-threshold is a separate independent task without solution hints or a worked example. The prior larger curriculum and games remain in the repository for history, but are outside this active journey.

## The learning loop

**Short idea → code game → own starter solution → related task → independent transfer.**

Keep the initial idea to one useful rule and a small code example. Let unfamiliar syntax open an explanation in place. Ask for a prediction or rough plan without requiring a specific phrase or grading private notes.

Run the first imperfect attempt. Compare one failing input, its expected return, and its actual return. Change the smallest relevant part. A syntax error and a logical error are useful clues, provided feedback helps the learner decide what to inspect.

Close a worked example before rewriting. A pass after help is supported practice. It becomes stronger evidence when the learner can explain the rule and solve a changed problem with less help.

## C.C. as a companion

Use the requested Code Geass theme through a restrained forest green, warm cream, and coral orange interface, a compact guide, and a Geass-inspired symbol. The character supports the workspace; there is no oversized action-poster hero.

C.C. currently uses authored content, not an LLM. Keyword explanations, brainstorming prompts, graduated hints, and real test evidence make her useful without generated chat. Expressions change on actual planning, run, success, bug, and hint events. Thoughtfulness can accompany uncertainty; concern stays encouraging.

Do not claim that keyword definitions, plans, or a friendly expression demonstrate understanding. Avoid celebrating a guided clear as independent mastery.

## Evidence and persistence

- Guided game evidence and drafts are separate from studio code records.
- Studio first score, attempts, later pass, and recorded help remain distinct.
- Custom inputs support experiments but do not award passes.
- Python replay records actual execution, capped at 180 events per test.
- Java provides compiler diagnostics and test evidence; it has no variable replay.
- Local storage preserves existing v0.2/v0.3 records under the same key.
- Optional before/after/48-hour checks contain five code-reading or code-gap problems. They complement independently written code.

The independent task removes solution hints and worked examples. General keyword help and a place for private notes remain available. Output tests alone cannot detect copying or prove an algorithm choice. Ask the learner to explain and adapt the solution.

## What is deferred?

Backend accounts, an AI tutor, hosted model inference, remote analytics, and a full DSA curriculum remain future work. No public deployment was performed. First observe whether a beginner moves from guided code to their own working solution.

Use the self-test record to identify the next change. Expand only after repeated sessions reveal what beginners can now do independently.
