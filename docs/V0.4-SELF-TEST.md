# v0.4 self-test — Can I now write it myself?

Use the prototype on yourself before expanding the curriculum. The question is whether an interaction changes what you can code independently.

Use the same browser address throughout. Export the notebook before resetting. Start with one language so switching syntax does not obscure what you learned; try the other language later as a separate observation.

## Before learning

Take the optional five-problem starting check before any regular studio pass. Choose “I don’t know yet” when needed. Record confidence honestly.

Write one sentence in the notebook: “Without help, I think I could write…” Do not study reference solutions or prepare answers for the later checks.

## One connected learning session

1. **Predict.** Read the short idea. Explain the input and promised return. Predict what one example will do before running it.
2. **Play with actual code.** Complete, repair, reorder, or write source in the guided game. Confirm that changed source changes the result.
3. **State the rule.** In plain words, describe what must be remembered, what repeats, and when to return. Use your own words, not the example's phrasing.
4. **Code from the studio starter.** Close the game/example. Write the matching function from its starter. Guided game evidence should not count as a studio pass.
5. **Debug one useful mistake.** Follow a failing input. Compare expected and actual returns. For Python, inspect the real line/variable trace. For Java, use the compiler line or follow the chosen input manually.
6. **Try a related task.** Change the requirement: choosing a maximum rather than summing, rotating a row, or counting values above a threshold. Explain which idea stayed useful.
7. **Transfer independently.** Attempt count-above-threshold without opening outside answers. Its private notes and general word definitions remain available, but no strategy hints or worked solution should appear.
8. **Return later.** After at least three regular studio passes, take the optional after-learning code check. Come back at least 48 hours later for different code-reading problems, then write a fresh small program before revisiting examples.

Do not copy references during the experiment. If you choose a worked example during practice, record it, close it, and rewrite later. The app records built-in help, but it cannot see help used elsewhere.

## Observe C.C. and the interaction

- A planning or hint action should produce a thoughtful reaction.
- Running actual code should show attention to the experiment.
- A pass should show quiet pride, alongside a reminder to explain or adapt.
- A syntax error, runtime error, or failing result should prompt a kind investigation.
- Expression changes should follow actual events, not a decorative timer.
- Keyword help should answer a small syntax question without replacing your whole solution.
- Hints should leave a next decision for you. Independent work should remain your own.

If the character distracts from writing, reduce its size or frequency. A helpful guide makes the next thought clearer.

## Useful edge cases

Choose custom inputs before running them and write the expected result yourself. Try zero, equal inputs, negatives, an empty array, one value, repeated values, or a route that returns to the origin when the task contract permits them.

Custom runs must not alter the mission score. A fixed answer that fits the first example should fail when inputs change. A long-running program should be stoppable without losing the draft.

## Record learning evidence

For each task, note the first score, final result, number of attempts, help used, the bug you understood, and whether you could explain the rule afterward. Record one changed problem you solved without the example.

A game clear, supported coding pass, independent solution, code-reading score, and delayed recall are separate evidence. Compare equivalent tasks, and do not combine older-version arithmetic/theory checks with v0.4 code-check scores.

One learner's improvement is a reason to test the design further, not proof of general teaching effectiveness.

## Functional smoke check

Run `npm test` and `npm run build`, then inspect the app through the local server.

- Onboard on phone and desktop widths; use both language switches.
- Complete and run a game, then open its studio starter.
- Produce and repair one real Python error and one Java compiler error.
- Inspect a failing test, Python trace, and an ungraded custom input.
- Refresh and confirm notes, language drafts, and separate game/studio evidence persist.
- Open the independent task and confirm there are no solution hints.
- Export the notebook. Check keyboard navigation, editor Tab escape, mobile navigation, and close/return focus for help dialogs.

Use a disposable journey for reset checks. The 48-hour gate is a real delay; do not change the clock in the learning experiment. Maintainer tests may check timing separately.
