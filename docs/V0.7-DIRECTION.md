# v0.7 — C.C. helps with the next line of code

The core stays beginner-first Python/Java, limited concepts, games that lead to real coding, and independent checks. No curriculum expansion or LLM was added.

## Decisions

- Replace four generic help tabs with three tools tied to the current draft: Fix code, Try input, Step through. Words, plans, and notes remain secondary.
- Keep the editor available alongside C.C. on desktop. Phone users get a closeable coach sheet.
- Spacing fixes change leading whitespace only, preserve every statement, require a real Python syntax check, and show a review before applying. Draft changes cancel stale work. Applying a fix records assistance and remains undoable. Passing syntax does not establish correct block meaning.
- Shrink a failed array input by running shorter inputs against the student's actual source and authored task contract. Bound the search to 24 candidates. Never claim a globally minimal counterexample. This is optional and ungraded; independent tasks exclude it.
- Input experiments accept readable values. Test deals use existing task cases. Nothing auto-solves or auto-runs on a card deal.
- Actual Python walkthroughs show initial inputs and changes after a line. Ignore module-loading trace events. Java keeps real compiler and test evidence, with no fabricated variable replay.
- C.C. uses authored reactions: hello, test challenge, thinking, concern, success. Keep reactions short and offer saved calm mode and reduced motion.
- Retain all progress keys, notes, real URLs, debug repair/rebuild separation, and first-attempt records.

## Frontend

## Learning trial

Start with a broken loop. Use one clue to identify a failing input; explain why it fails before editing. Write the fix, run it, then close C.C. and solve a related fresh task. Record which interaction helped you decide the next line. Repeat later without the original source. Keep learning outcomes separate from test passes.
